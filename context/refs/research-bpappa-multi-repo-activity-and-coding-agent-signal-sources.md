# Multi-Repo Activity Overview Tools and Coding-Agent Ecosystem Signal Sources — Best Practices, Anti-Patterns, Prior Art

Scope: identify additional `Signal(source, kind, timestamp, summary, ref)` sources for `project-commander` beyond the seven already-implemented scanners (`git`, `claude`, `gemini`, `omp`, `opencode`, `kiro`, `docs`) and the documented `bd` candidate. Constraint: every recommendation must have a discoverable per-project anchor (file or directory pattern) and time-stamped events (or mtime as a proxy).

## Best Practices

- **Use a discoverable per-project anchor that does not require state files.** ghq encodes provenance directly in directory layout (`~/ghq/<host>/<user>/<repo>`), so no separate registry is needed; presence of the path is the index. — https://github.com/x-motemen/ghq · README "DIRECTORY STRUCTURES" (Tier 1)
- **Read the agent's own session-list file as the source of truth, not directory mtime.** Continue.dev maintains `~/.continue/sessions/sessions.json` as a chronological metadata index with `workspaceDirectory` per session, plus `~/.continue/sessions/<sessionId>.json` per session, allowing direct per-project filtering without scanning every payload. — https://raw.githubusercontent.com/continuedev/continue/main/core/util/paths.ts , https://raw.githubusercontent.com/continuedev/continue/main/core/util/history.ts (Tier 1, primary source)
- **Treat the workspace-storage hash as a stable per-project key.** VSCode's `workspaceStorage/<id>/` folder ID is `md5(fsPath + inode)` on Linux (or `md5(fsPath + birthtime_ms)` on macOS/Windows), recomputable from a project path; this lets a scanner address VSCode-extension state per-project deterministically. — https://stackoverflow.com/questions/74155386/how-does-visual-studio-code-determine-the-workspacestorage-folder-for-a-given-wo cites https://github.com/microsoft/vscode/blob/cadabab73fef89fe0c4bfe23b5a33cd58e39ea9c/src/vs/platform/resource/node/resourceIdentityServiceImpl.ts#L30-L53 (Tier 1)
- **Prefer atomic-rename writes for any local state your scanner reads concurrently.** Cline writes its task files via temp-file + `fs.rename` to avoid partial-state reads; scanners over the same files should expect this and not fail-loud on transient `ENOENT`. — https://raw.githubusercontent.com/cline/cline/main/src/core/storage/disk.ts (Tier 1, primary source)
- **For batch git status across many repos, follow gita's two-axis model: branch-vs-remote color + working-tree symbols (`+` staged, `*` unstaged, `?` untracked, `$` stashed).** This is a documented convention for surfacing "is this repo busy" without inventing a new vocabulary. — https://raw.githubusercontent.com/nosarthur/gita/master/README.md (Tier 1)
- **Use compose project labels, not container names, to map runtime to a project.** Docker Compose tags every container with `com.docker.compose.project` (defaults to base directory name) — the canonical join key from container runtime back to a working tree. — https://docs.docker.com/compose/how-tos/project-name/ (Tier 1)

## Anti-Patterns

- **Do not treat absolute path strings inside agent storage as stable.** Cline stores per-task working-directory metadata in `task_metadata.json` under a UUID directory; the only reliable workspace pointer lives in a separate `state/taskHistory.json` index, and the path can drift if users move project dirs. Tools that join only on cwd string-equality miss historical sessions. — https://raw.githubusercontent.com/cline/cline/main/src/core/storage/disk.ts (Tier 1)
- **Do not assume agent storage is bounded.** Roo Code's `~/.config/Code/User/globalStorage/rooveterinaryinc.roo-cline/tasks/<uuid>/` directories accumulate without GC — a single user reported 435 GB across 5 task dirs because of unbounded checkpoint shadow-git repos. A scanner that reads every `api_conversation_history.json` end-to-end will be slow and may OOM; only stat metadata files. — https://github.com/RooCodeInc/Roo-Code/issues/4174 (Tier 2, GH issue, primary)
- **Do not parse VSCode's `state.vscdb` chat tables as a stable schema.** `state.vscdb` is an internal SQLite file VSCode treats as opaque; chat session schema changes between releases, and the trust state and chat history live in the same DB. Use it only as a fallback signal; prefer extension-specific globalStorage when available. — https://www.reddit.com/r/vscode/comments/1n1244j/where_is_the_json_setting_for_trusted_folders/ , corroborated by https://github.com/microsoft/vscode/issues/293737 (Tier 2)
- **Do not equate "tasks/<uuid>" presence with "active project".** The Roo/Cline task IDs are agent-internal and can include unrelated workspaces or system-level chats; resolution must go through the per-task workspace pointer or the `state/taskHistory.json` HistoryItem entries. — https://raw.githubusercontent.com/cline/cline/main/src/core/storage/disk.ts (lines around `readTaskHistoryFromState`) (Tier 1)
- **Do not rely on `.pre-commit-config.yaml` mtime as "active project".** Config files in repo root can be untouched for years while the repo is still active; use them as adoption markers, not activity proxies. (Inference from existing `flake.lock` / `package.json` lockfile-as-signal pattern in this project.)
- **Do not cite Pulse / GitHub Repository Insights as a local signal.** Pulse is a web-only summary view; it has no per-project local anchor and requires authenticated API calls — viable only as a Tier-3 fallback. — https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/using-pulse-to-view-a-summary-of-repository-activity (Tier 1, but no local anchor)

## Prior Art

### Multi-repo / git-fleet overview tools

- **myrepos (`mr`)** — uses a single registry at `~/.mrconfig` populated by `mr register`; `mr update`, `mr status`, `mr commit` recurse over all registered repos. Discovery method only; per-repo activity comes from delegated VCS commands. — https://myrepos.branchable.com/ (Tier 1, primary)
- **gita** — registry at `$XDG_CONFIG_HOME/gita/repos.csv` (typically `~/.config/gita/repos.csv`); `gita ll` displays branch + 4-symbol working-tree status (`+ * ? $`) + 5-color local-vs-remote relationship side-by-side. The status colour-coding is the documented convention. — https://raw.githubusercontent.com/nosarthur/gita/master/README.md (Tier 1, primary)
- **ghq** — convention-based directory layout under `ghq.root` (default `~/ghq/`) as `<host>/<user>/<repo>`; configured via git-config `ghq.root` (multi-valued). Activity not surfaced by ghq itself — it is a discovery mechanism that other tools can layer on. — https://github.com/x-motemen/ghq (Tier 1, primary README)
- **lazygit** — global state at `~/.local/state/lazygit/state.yml` (Linux) / `~/Library/Application Support/lazygit/state.yml` records recent repo paths; per-repo override at `<repo>/.git/lazygit.yml` and `<repo>/.lazygit.yml`. Recent-repo list is a per-machine activity signal. — https://raw.githubusercontent.com/jesseduffield/lazygit/master/docs/Config.md (Tier 1, primary)
- **GitRepoMonitor (.NET desktop tool)** — scans the user's machine for existing repos, periodically pulls, surfaces ahead/behind. Demonstrates the "auto-discover all repos under home dir" pattern as opposed to explicit registration. — https://github.com/elsantner/GitRepoMonitor (Tier 2)
- **GitHub Pulse / Repository Insights** — web-only summary surfaced via the GitHub API: PRs/issues opened-and-closed in 1d/7d/30d, commit count, top contributors. No local anchor; requires auth; useful only as a Tier-3 enrichment. — https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/using-pulse-to-view-a-summary-of-repository-activity (Tier 1)
- **`chops` (Shpigford)** — example of a desktop multi-agent dashboard built specifically because "skills are scattered across all over your machine"; aggregates state from Claude Code, Cursor, Codex, Windsurf, Copilot, Aider, Amp. Confirms the signal-aggregation pattern is mainstream. — https://github.com/Shpigford/chops referenced via https://www.threads.com/@aibymayank/post/DWRJQVkklHZ (Tier 3, social post citing repo)

### Coding-agent per-project storage conventions (excluding the 7 already implemented + bd)

- **Aider** — at git root: `<repo>/.aider.input.history` (timestamped one-line-per-prompt log) and `<repo>/.aider.chat.history.md` (markdown rolling transcript). Defaults are computed in `aider/args.py` from `git_root`. Optional `--llm-history-file` adds `<repo>/.aider.llm.history`. Repo example: timewarp-simple-icons checks in its `.aider.chat.history.md`. — https://raw.githubusercontent.com/Aider-AI/aider/main/aider/args.py (Tier 1, primary source); example commit at https://github.com/TimeWarpEngineering/timewarp-simple-icons/blob/main/.aider.chat.history.md
- **Cline** — `~/.config/Code/User/globalStorage/saoudrizwan.claude-dev/tasks/<taskId>/` containing `api_conversation_history.json`, `ui_messages.json`, `task_metadata.json`, plus `~/.config/Code/User/globalStorage/saoudrizwan.claude-dev/state/taskHistory.json` as the workspace-to-task index. — https://raw.githubusercontent.com/cline/cline/main/src/core/storage/disk.ts (Tier 1, primary)
- **Roo Code** — `~/.config/Code/User/globalStorage/rooveterinaryinc.roo-cline/tasks/<uuid>/` with the same shape as Cline (Roo is a Cline fork). Per-task file structure documented in users' bug reports. — https://github.com/RooCodeInc/Roo-Code/issues/4174 ; https://www.reddit.com/r/RooCode/comments/1kr12f4/sync_settings_tasks_mcps_between_devices/ (Tier 2)
- **Continue.dev** — global storage `~/.continue/` (overridable via `$CONTINUE_GLOBAL_DIR`); sessions at `~/.continue/sessions/sessions.json` (chronological list of `BaseSessionMetadata` including `workspaceDirectory`) and `~/.continue/sessions/<sessionId>.json` (full session). Dev-data event log: `~/.continue/dev_data/<schema>/<eventName>.jsonl` and SQLite at `~/.continue/dev_data/devdata.sqlite`. — https://raw.githubusercontent.com/continuedev/continue/main/core/util/paths.ts , https://raw.githubusercontent.com/continuedev/continue/main/core/util/history.ts (Tier 1, primary)
- **Zed agent panel** — config at `~/.config/zed/` (Linux/freebsd via XDG); data at `~/.local/share/zed/` (`$XDG_DATA_HOME/zed`); SQLite database directory `~/.local/share/zed/db/`; user prompts at `~/.config/zed/prompts/` (Linux) or `~/Library/Application Support/Zed/prompts/` (macOS). Conversation/thread state lives in the SQLite db, keyed by internal IDs — not natively per-project. — https://raw.githubusercontent.com/zed-industries/zed/main/crates/paths/src/paths.rs (Tier 1, primary)
- **GitHub Copilot Chat (VSCode extension)** — chat sessions land in the workspace's `state.vscdb` at `~/.config/Code/User/workspaceStorage/<md5(path+inode)>/state.vscdb` (Linux); workspace folder is keyed by md5 hash derived from absolute path + inode/birthtime. Schema is internal and unstable. — https://stackoverflow.com/questions/74155386/how-does-visual-studio-code-determine-the-workspacestorage-folder-for-a-given-wo ; https://github.com/microsoft/vscode/issues/293737 (Tier 1/2)
- **Windsurf (Codeium)** — VSCode-fork product; rules file `.windsurfrules` at project root is the project-level adoption marker (referenced by other agents as a known rules path). Per-session storage is internal to the fork's user-data dir under `~/.config/Windsurf/User/...` (mirrors VSCode layout). — https://raw.githubusercontent.com/cline/cline/main/src/core/storage/disk.ts (Cline lists `.windsurfrules` as a peer rules file); https://gist.github.com/danielrosehill/ec279319741ed74143052ddce9132b1e (Tier 2)
- **Sourcegraph Cody (VSCode)** — extension `sourcegraph.cody-ai`; chat history is stored locally in the VSCode globalStorage namespace and downloadable as JSON. Path follows VSCode convention: `~/.config/Code/User/globalStorage/sourcegraph.cody-ai/`. Exact filename schema is undocumented — per-project resolution is via the VSCode workspaceStorage hash. — https://sourcegraph.com/docs/cody/clients/install-vscode (Tier 2)
- **Cursor agent transcripts** (already documented as candidate, listed for completeness): `~/.cursor/projects/<encoded-cwd>/agent-transcripts/*.{json,txt}` and SQLite `~/.cursor/chats/<hash>/<uuid>/store.db`.

## Missed Signal Categories (outside agent CLIs)

- **Container runtime state** — Docker Compose tags every container/network/volume with `com.docker.compose.project=<name>` (default = base directory of compose file) and `com.docker.compose.project.working_dir=<abs path>`. `docker ps --filter label=com.docker.compose.project=<basename>` joins running infrastructure to a project. — https://docs.docker.com/compose/how-tos/project-name/ (Tier 1)
- **CI run history (remote)** — `gh run list -R <owner>/<repo> --json conclusion,createdAt,headBranch,status,workflowName` returns recent workflow runs; existing `.github/workflows/` presence is the local discovery anchor. Requires authenticated `gh`. — https://cli.github.com/manual/gh_run_list (Tier 1)
- **Test/lint/type cache mtime** — `.pytest_cache/v/cache/lastfailed`, `.pytest_cache/v/cache/nodeids`, `.ruff_cache/`, `.mypy_cache/`, `.tox/` — file mtime is "last test/lint/typecheck run" for that tool. The pytest cache plugin is enabled by default and is the documented re-run mechanism. — https://docs.pytest.org/en/stable/how-to/cache.html (Tier 1)
- **Devcontainer / Codespace markers** — `<repo>/.devcontainer/devcontainer.json` (or root `.devcontainer.json`) marks devcontainer-aware projects. Spec: https://containers.dev/implementors/spec/ (Tier 1) ; GitHub Codespaces uses the same file. — https://docs.github.com/en/codespaces/setting-up-your-project-for-codespaces/adding-a-dev-container-configuration/introduction-to-dev-containers (Tier 1)
- **Pre-commit / hook config** — `<repo>/.pre-commit-config.yaml`, `<repo>/.husky/`, `<repo>/lefthook.yml` are adoption markers; mtime ≈ last toolchain change. (Inference; same pattern as `flake.lock`.)
- **Tool-version markers** — `.tool-versions` (asdf), `.mise.toml`/`mise.toml` (mise), `.python-version`, `.nvmrc`, `.ruby-version`. Adoption signal + churn proxy.
- **direnv adoption** — `<repo>/.envrc` plus state at `~/.local/share/direnv/allow/<sha>` for per-project allow. Indicates an actively-developed working tree (direnv only fires on `cd`). — https://direnv.net/ (Tier 1)
- **Build daemon / LSP cache mtime** — `target/` (Cargo + rust-analyzer index), `node_modules/.cache/`, `.next/`, `.turbo/`, `.gradle/`. High noise but useful as "last build" proxy.
- **VSCode / JetBrains workspace state** — `~/.config/Code/User/workspaceStorage/<md5>/` (last-write mtime ≈ last editor session). Already partially covered by JetBrains in current scope; VSCode equivalent is missing. — https://stackoverflow.com/questions/74155386/how-does-visual-studio-code-determine-the-workspacestorage-folder-for-a-given-wo (Tier 1)
- **Editor "recent / pinned" lists** — lazygit `state.yml`, `gh repo view` recents, `tldr`/`thefuck` shell histories, `fzf` history. Most overlap with already-implemented zsh history, but lazygit specifically tracks recent repos. — https://raw.githubusercontent.com/jesseduffield/lazygit/master/docs/Config.md (Tier 1)
