# `dod` walkthrough

A reproducible end-to-end demonstration of the `dod` subcommand. The
`walkthrough.sh` script builds three sandbox projects under a temp
directory, walks one of them from "mid-flight" to "shipped" across six
transitions, and runs `dod` at each one so you can see the relative
diff and progress evolve.

The captured outputs in [`expected-outputs/`](expected-outputs/) are
exactly what the script produces against this version of the tool, and
exist so you can read the example without running anything.

## Run it

From the repo root:

```sh
PCMD=".venv/bin/python -m project_commander" \
  examples/dod-walkthrough/walkthrough.sh
```

Or, if `project-commander` is installed on `PATH`:

```sh
examples/dod-walkthrough/walkthrough.sh
```

The script builds a sandbox under `$(mktemp -d)`, runs the journey, and
deletes the sandbox at the end. Pass `--keep` to leave it in place for
inspection. Captured per-step outputs are written under
`/tmp/dod-walkthrough-out.*` regardless of the cleanup mode.

## What you see

Headline output (one line per transition):

```
T0    Confirm by hand and tick `User has reviewed the README` in DOD.md (78%)
T1    Address `Working tree clean`: 1 uncommitted file(s) (40%)
T2    Address `Pushed to origin`: origin/main: 2 ahead (50%)
T3    Address `Pushed to origin`: origin/main: 3 ahead (60%)
T4    Confirm by hand and tick `User has reviewed the README` in DOD.md (80%)
T5    Definition of Done met. (100%)
```

Then a fleet roll-up across the three sandbox projects:

```
  OPEN  [░░░░░░░░░░░░]  0/3   api-rewrite  Address `Working tree clean`: 1 uncommitted file(s)
  DONE  [████████████]  10/10 wordcount    Definition of Done met.

1 of 2 project(s) with DOD.md are complete.
1 project(s) have no DOD.md: quiet-tool
```

## The story

The `wordcount` sandbox project starts with a `DOD.md` listing ten
closure criteria — eight auto-checkable, two requiring user
attestation. The script then advances the project through six states:

| step | what changed                                            | progress  | percent |
|------|---------------------------------------------------------|-----------|---------|
| T0   | baseline (DOD.md committed; no work yet)                | 7/9       | 78%     |
| T1   | mid-flight (dirty tree, plan open, ahead of origin)     | 4/10      | 40%     |
| T2   | commit code                                             | 5/10      | 50%     |
| T3   | tick all plan checkboxes; document usage                | 6/10      | 60%     |
| T4   | push to origin                                          | 8/10      | 80%     |
| T5   | tick the two MANUAL items                               | 10/10     | 100%    |

Five things to notice as you read the captured outputs:

1. **`T0 = 78%` is honest, not inflated.** A freshly scaffolded clean
   repo really does pass most mechanical checks vacuously. The two
   `MANUAL` items are the only outstanding work at that point.

2. **Adding `PLAN.md` at `T1` lowers the percent.** The denominator
   grew when a previously-`SKIP`ed criterion (`All plan phases
   complete`) became relevant. New structure represents new tracked
   work; the score reflects honest reality, not a number that only ever
   goes up.

3. **`T1 → T2` shows a partial repair.** Committing the staged file
   flips `Working tree clean` from `FAIL` to `PASS`. The `Verify
   passes` criterion stays `FAIL`, but its detail evolves
   (`2 verify check(s) failed → 1 verify check(s) failed`) — the same
   status, a measurably smaller failure. An agent loop can key on the
   detail string even within an unresolved criterion.

4. **`next_action` pivots category at `T4`.** Once every `FAIL` is
   cleared, the suggestion shifts from `Address ...` to `Confirm by
   hand and tick ...`. The two `MANUAL` items are the only thing left,
   and the tool is explicit that this is now a user-attestation phase,
   not an agent-do-more-work phase.

5. **`T5` is `DONE` and exit code is 0.** The script asserts this
   contract. If a future change to `dod` ever stopped honoring "all
   PASS + DONE → exit 0", the script fails loudly.

The expected-outputs folder is regenerated by re-running the script and
copying `/tmp/dod-walkthrough-out.*` over it. Anything the script
produces that ends up out of date here is a real difference worth
explaining in the diff.

## The agent driver loop, concretely

The JSON form is the contract surface for chaining. A driver loop:

```python
import subprocess, json

def step():
	out = subprocess.run(
		["project-commander", "dod", "--project", "wordcount",
		 "--root", "/path/to/code", "--format", "json"],
		capture_output=True, text=True,
	)
	return json.loads(out.stdout), out.returncode

while True:
	state, rc = step()
	if rc == 0:
		print("Definition of Done met. Shipping.")
		break

	print(f"[{state['percent']}%] {state['next_action']}")

	fail = next((c for c in state["criteria"] if c["status"] == "FAIL"), None)
	if fail is not None:
		# `fail['detail']` carries the hint:
		#   "1 uncommitted file(s)", "origin/main: 2 ahead", etc.
		handle_fail(fail)
		continue

	manual = next((c for c in state["criteria"] if c["status"] == "MANUAL"), None)
	if manual is not None:
		prompt_user(manual["text"])  # only the user can resolve this
		break
```

Three properties make this work:

1. **Exit code is the loop condition** (`rc == 0` ⇒ done). No JSON
   parsing required just to stop.
2. **`next_action` is one string**, not a list — the agent doesn't have
   to pick a strategy.
3. **The `criteria` array is the structured backup** when the
   one-string `next_action` is too coarse. Each entry carries
   `status`, `detail`, and `auto_check` so the agent can reason at
   whatever granularity it needs.
